# Requirements and verification

This page provides stable library-level requirements and maps them to current evidence. It is a maintainable traceability baseline, not a substitute for the CubeSpec system requirements or the electrical ICD. "UT" means host or F Prime component unit test, "IT" means host integration test, "Inspection" means source/design review, and "HIL" means measurement on real hardware. Host tests are in `tests/`; F Prime component tests are the `Adxl355_Manager_ut_exe` and `Adxl355_Application_ut_exe` executables. Executed results are retained in `docs/evidence/`.

Parent requirements are CubeSpec system requirements that have not yet been allocated to this library; the "Rationale / parent" column records why each requirement exists until those IDs are assigned. Data-sheet references are to ADXL354/ADXL355 Rev. D.

| ADXL-DEV-013 | An acquisition read shall return `FROZEN_DATA`, without replacing the caller's sample, when `DATA_RDY` is set and X, Y and Z equal those of the read before for `FROZEN_REPEAT_LIMIT` (8) reads in a row. ## Deployment and HIL requirements

These are integration requirements. They cannot be closed by the library's emulator tests.

| ID | Requirement | Rationale / parent | Verification status |
| --- | --- | --- | --- |
| ADXL-INT-001 | The deployment shall open one mode-0 SPI endpoint per chip select at no more than 10 MHz before manager initialization. | Data sheet SCLK limit 10 MHz. | Raspberry Pi bench or flight-target HIL; procedure documented, not executed in this repository |
| ADXL-INT-002 | The deployment shall invoke `acquireFrame` from one timing task, shall connect the application's and every manager's `schedIn` to one rate group that runs below that task's priority, and shall size command-dispatcher health-ping timeouts for the documented initialization bound (about 5.4 s for seven sensors), or route initialization through an active component. | The library serializes access but initialization blocks its caller; without `schedIn` the fault edges are never reported. | Topology/execution-context analysis required per deployment |
| ADXL-INT-003 | The external-synchronization deployment shall hold the 1.024 MHz clock and the synchronization pulses low while it initializes the sensors, a reinitialization included. It shall then start and stabilize the clock, start the pulses, and enable acquisition only after at least one filter group delay of pulses. | Until initialization writes `SYNC` (`EXT_CLK` = 1, `EXT_SYNC` = 01), and again from the software reset it starts with, `INT2` and `DRDY` are outputs (data sheet Table 14). Driving them then contends with the sensor, so the CubeSpec ACC board design notes configure the sensors before the clock starts. Initialization needs no external clock: register access runs on SCLK. Data sheet DRDY section: one to three samples after the first synchronization pulse can be lost or corrupted. | Flight-target HIL and signal capture required |
| ADXL-INT-004 | The full seven-sensor acquisition path (seven 14-byte status-checked reads) shall complete with verified margin inside its 250 microsecond period under worst-case flight CPU and I/O load. | 78.4 microseconds of bus time at 10 MHz before overhead. | Flight-target timing measurement required |
| ADXL-INT-005 | The deployment shall monitor the synchronization pulse train and the per-sensor status for stale, frozen, implausible, and busy results, and shall contain a failed or stalled sensor without suppressing healthy samples. | Loss of SYNC alone is not visible to the sensor path. | F Prime integration test plus HIL fault injection required |
| ADXL-INT-006 | Science processing shall apply controlled per-sensor calibration, axis mapping, and temperature compensation above this transport library. | Transport library uses typical sensitivities. | CubeSpec calibration and application-level verification required |
| ADXL-INT-007 | The deployment shall power-cycle the sensors before the first initialization after a flight-software restart, or accept that the NVM shadow reference may have been captured after an earlier software reset. | The shadow reference is only valid if captured before any software reset since power-up. | Operational procedure and HIL reset test required |
| ADXL-INT-008 | HIL shall confirm on real silicon that STATUS bits 7:5 read 0 and that `DATA_RDY` clears on a STATUS read in the flight synchronization mode. | The plausibility and freshness checks rely on these data-sheet properties. | Raspberry Pi bench and flight-target HIL required |

## Maintaining traceability

When behavior changes:

1. update the requirement or add a new stable ID;
2. update the design and API documentation;
3. add a test that fails before the implementation change;
4. place the exact test name or HIL artifact in the verification column;
5. rerun the suites, refresh `docs/evidence/`, and regenerate the manifest with `python3 tests/check_evidence.py --update`; and
6. do not mark an electrical, timing, or flight-target requirement verified from host-only evidence.
